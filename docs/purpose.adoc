= pftree: purpose
:toc:

== Abstract

pftree answers one question about a directory tree and then lets a caller act on the answer: which directories hold files, and which files. It records the answer as a mapping from directory to file names, offers filters that narrow it, and runs a read, analyze and write sequence over every directory that remains, mirroring the input layout into an output tree. The package exists because that sequence recurs in almost every tool that processes medical imaging data on a filesystem, and writing it once, with its failure modes handled, is cheaper than writing it in each tool.

== The problem

Imaging data on disk is organized by directory. A DICOM series is a directory of slices; a FreeSurfer subject is a directory of volumes and surfaces; a BIDS dataset nests subjects, sessions and modalities as directories. A tool that converts, anonymizes, measures or renders such data therefore works per directory, not per file, and its first job is always the same: find the directories that matter, decide which of their files are inputs, and put the outputs somewhere that preserves the relationship to the inputs. Done ad hoc, this job is repeated in every tool, each with its own walk, its own notion of a filter, its own way of failing when one directory is unreadable, and its own idea of where output goes.

The ChRIS platform sharpens the need. A ChRIS plugin receives an input directory and an output directory and nothing else; whatever structure it finds under the first it must reproduce under the second. Plugins that share a walk behave alike, can be filtered alike from the platform's user interface, and fail alike when data is malformed. Plugins that do not share one cannot.

== What pftree is

pftree is a Python package with an engine class, `Pftree`, and a command, `pftree`. The engine walks an input directory once with `os.scandir`, stat-ing every entry as it goes, and produces three things from that single pass: the `tree`, which maps each directory holding files to the sorted names of those files; one `DirNode` per directory, carrying its path, its path relative to the input root, its files with their sizes, and the output path that corresponds to it; and the cumulative disk usage of every directory in post-order, which is the report `du` prints.

Two filters narrow the tree. A file filter tests names; a directory filter tests the path relative to the input root. Each takes comma-separated tokens that are substrings, shell globs, regular expressions or negations of those, combined under AND or OR. The two filters are always ANDed, because a file that passes in a directory that does not is not an input, and a directory left with no files leaves the tree.

Processing is three callbacks, read, analyze and write, called in that order for every directory. Reads and writes run sequentially; analyses run in a thread pool when asked. A callback receives the `DirNode` and returns a `StageResult` whose `status` says whether the directory succeeded. A directory whose analyze fails, or whose callback raises, is logged with its traceback and dropped before the write stage, and the run continues with the rest; a run fails only when every directory did. This is the behaviour a batch over thousands of series needs: one bad series should cost one series, not the batch.

The command exposes the engine without a subclass. It prints the tree as JSON, runs the three stages with demonstration callbacks under `--test`, and, with `--du`, prints byte for byte what `du -k` prints, so that `pftree --du --inputDir /data | xdu` works. The `du` compatibility is deliberate: a tool that reports sizes in a format no other tool reads has reported them to no one.

== What pftree is not

pftree does not map files one to one. A tool whose unit is a single file, read here and written there, is better served by a plain file iterator; pftree's directory grouping would be a detour. pftree also knows nothing of ChRIS, CUBE or any store; it reads and writes a filesystem, and a plugin built on it is a ChRIS plugin because of its wrapper, not because of pftree.

== pftree and PathMapper

The ChRIS plugin template ships `chris_plugin.PathMapper`, and a plugin author choosing a walk should know how the two differ, since each is the right tool for a different shape of plugin.

`PathMapper` is an iterator of pairs. Given an input directory, an output directory and a glob, it yields each matching input path together with the output path that corresponds to it, creating parent directories as it goes; `file_mapper` yields files, `dir_mapper_shallow` the immediate subdirectories, `dir_mapper_deep` the deepest ones. A `filter` callable narrows the matches, a `name_mapper` renames outputs, and `fail_if_empty` exits the process when nothing matches. It is about three hundred lines, has no dependencies and no opinions, stats nothing, and stops there. For a plugin whose unit of work is one file, read here and written there, it removes exactly the code that plugin would otherwise write, and nothing pftree adds would be used.

pftree's unit is the directory, and the difference follows from that. A `DirNode` carries the directory, its path relative to the input root, its files and their sizes, and its output path, so a plugin that works per series, subject or session does not rebuild that grouping from a stream of files. The three-stage contract gives every plugin on it the same failure semantics, one bad directory logged and dropped while the rest proceed, and the same thread pool, where with `PathMapper` each plugin writes its own loop, its own error handling and, usually, no threading at all. The filters are options a user sets at run time rather than a callable fixed when the plugin is written, and the single-pass scan yields sizes and a `du`-exact report that a plugin asking "how large is this input" gets without a second walk. The command line and manual parts let the plugins built on pftree share one vocabulary of options and one page layout.

What pftree does not offer is `PathMapper`'s per-file mapping and output renaming, or its footprint: pftree asks a plugin to think in directories and in three stages, and a plugin that has no directory notion pays that for nothing. Neither knows anything of CUBE or any store; both stop at the filesystem.

The choice, then, is by the plugin's unit of work. One file in, one file out: `PathMapper`. One operation per directory, with filters, failure isolation and parallelism wanted: pftree. The members of the pfdo and pfdicom families are the second kind, which is why they are built here.

== Who uses it

pftree is the base of two families. The `pfdo` family (`pfdo`, `pfdo_run`, `pfdo_med2image`, `pfdo_mgz2image`, `pfdo_mri_unet`) subclasses it to run one operation per directory. The `pfdicom` family (`pfdicom`, `pfdicom_tagExtract`, `pfdicom_tagSub`, `pfdicom_rev`, `pfdicom_agesort`) subclasses it to read, rewrite and summarize DICOM headers per series. The ChRIS plugins built on those (`pl-shexec`, `pl-pfdicom_tagExtract`, `pl-pfdicom_tagSub` and others) inherit the walk, the filters and the failure semantics, which is the point.
